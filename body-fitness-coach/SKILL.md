# Body Fitness Coach

Use `.private/.venv/Scripts/python.exe scripts/coach.py` relative to this skill. The script defaults to `.private/private.db`, so do not pass `--data-dir` for the normal local installation. `.private/` is gitignored and is the only place in this folder allowed to contain identifiers, measurements, runtime files, or exported personal data; never place them in tracked files.

When explicitly activated in a fresh or reset session, run `doctor` once. Confirm that its `state` points to this skill's `.private/private.db` and that `history` is non-empty before recording, analyzing, or sending anything. If `.private` or its interpreter is missing, run `powershell -File scripts/install.ps1`; do not create a second data directory.

## Choose the operation

| Request | Action |
| --- | --- |
| Analyze data or preview a report | Use `daily --dry-run`, `weekly --dry-run`, or `doctor`; these may read sources but must not send or write externally. |
| Send a daily/weekly report | Ask for confirmation immediately before running without `--dry-run`; use `daily --force` only for an explicitly requested resend. |
| Record food from text/photo | Infer meal type, foods, portions, and nutrition from the message, photo, time, and recent context, then write immediately without confirmation. Ask only when the meal cannot be identified well enough to create a useful record. Then pass JSON through `food --json-file ... --source-id ...`. |
| Record personal body knowledge | When the user provides a report, measurement, body image, supplement, available equipment, medical history, symptom, or any other durable fact useful for future body/training advice, record it locally without asking for a second confirmation. Follow the knowledge workflow below. |
| View or use personal body knowledge | Use `knowledge status`, `knowledge search`, or `knowledge show`. Retrieve only the relevant entries for the current task. |
| Change a training template | Show the concrete diff and obtain separate confirmation. After approval, update the living Lark training manual, append its dated change record, record the same change in the private knowledge base, and sync the mirror. Reports may recommend changes but never apply them. |

Food JSON must contain `foods`; every item needs `meal_type`, `name`, `amount`, `unit`, `date`, and `ntr`. Use `breakfast`, `lunch`, or `dinner` for `meal_type`; the script canonicalizes common Chinese and Xunji aliases and rejects unknown values before calling Xunji, so never bypass `food` by posting natural-language meal names directly. Prefer a reasonable ordinary-serving estimate over a clarification round, and state the important portion or nutrition assumptions after writing so the user can correct them. After every food write, report calories, protein, carbohydrates, and fat for both the recorded meal and the day's cumulative total, alongside the daily targets when available. Xunji may attach a configured nutrition target only to an older dated food row while newer API-created rows contain zero limits, so search the bounded target-history window for the newest non-zero target; never describe an empty parse as proof that the user has no target, and instead report that the target could not be read.

## Meal reminder forms

The meal reminder supports one dropdown and one custom text input per missing meal. `scripts/meal_forms.py` builds up to five combinations per meal from the previous 30 days of Xunji records, ranked by frequency then recency. Dropdowns use numbered titles listing every food, without truncation or item-count abbreviations; breakfast titles put buns or other staples first and milk/tea eggs last. Keep the card compact: no combination detail panels; put the report date in the card title and start the body directly with breakfast, without introductory text, label the Other section only as 其他 with no description, and keep full quantities only in the private snapshot used for recording. Identical food/quantity combinations with a different entry order count together. Choices are recomputed for each new card, excluding the current day's incomplete meals; a new meal can therefore enter the choices from the next day, subject to ranking. Already sent cards keep their snapshots. Custom text replaces the selected combination for that meal; blank meals are skipped. Submitting is permission to record the filled meals. It returns meal nutrition, daily totals and targets. A repeated click, an already recorded meal, a different user/chat, or an old-date card must not create another meal.

The bottom Other section accepts snacks, late meals and supplements separately from the three main meals. Its multi-select presets use the latest matching historical nutrition values for protein powder (35g, water-mixed) and one cup of milk (260ml); absent history is not fabricated. Both may be selected together. Custom Other text replaces the selected presets. By submission time, food uses `morning-added` before 11:00, `noon-added` from 11:00 to 16:59, or `night-added` thereafter; keep this rule in the skill instructions rather than adding explanatory text to the compact card. `food` also accepts these three canonical meal types and their Chinese aliases. Each card accepts one Other batch; repeated submission does not add it again. After success, a newly generated card permits another batch. For an explicitly requested card when all main meals are already recorded, run `meal-reminder --force`; the scheduled reminder still skips days with no missing main meal. Frequency ranking, card generation and preset recording are deterministic and make no model calls. Only parsing custom text uses model tokens; a surrounding agent conversation may also consume tokens.

This is a skill-owned **native bridge command**, like `/config`, not an agent callback. `scripts/bridge_meals.mjs` handles only `bodycoach.meal.<nonce>` and passes the form to the private Python runtime. It does not use `__bridge_cb` or `bridge_token`, forward unsigned payloads to an agent, or change the bridge's callback authentication. Custom text is parsed in a separate read-only model call and validated before any food write. No body knowledge is read. Snapshots, identities, locks and submission payloads stay in `.private/`.

Install or inspect the minimal bridge hook with `.private/.venv/Scripts/python.exe scripts/install_meal_bridge.py` (preview), then `--apply --owner-id <user-open-id>` when configuring the record owner. It adds only a `/bodycoach` handler importing this skill and backs up the original bridge file privately. Restart the bridge after installing the hook; do not enable a live form until the hook is loaded. Re-run the installer after a bridge package upgrade; it refuses unfamiliar builds. The normal skill installer also restores this hook. If `meal_owner_id` is absent, reminders retain the original text-card behavior. `meal-reminder --dry-run` previews without sending or saving a form snapshot. Validate changes with `scripts/test_meal_forms.py` and `node scripts/test_bridge_meals.mjs`.

When activating from inside the same bridge, use `powershell -File scripts/schedule_meal_activation.ps1 -AgentPid <pid> -BridgePid <pid>` (supports `-WhatIf`). It schedules `scripts/activate_meal_forms.py` once through Windows Task Scheduler using the private `pythonw.exe`. The helper waits for agent processes to exit, verifies the target bridge's identity, uses the existing sibling `lark-scripts/Bridge-Startup.ps1` launcher, checks that exactly one new bridge process runs, and sends the new reminder plus an activation result. Its status is `.private/meal-activation.json`. Do not claim live activation merely because this task was scheduled. On another installation without that launcher, restart through that installation's normal service manager instead.

Do not automatically clear a submission lock left by a crashed process or resend a food write whose outcome is uncertain. Inspect the current Xunji meal and the private `writes` entry first. Successful meals use stable per-form/per-meal request IDs; failures may be retried without re-adding completed meals. Use text messages for corrections to an existing meal.

When a message sent between 00:00 and 05:59 local time reports breakfast, lunch, and dinner as one completed daily record, assign all three meals to the previous calendar day unless the user explicitly gives another date. Do not infer the date from the message timestamp alone.

Strength templates are a reference library only; never maintain or advance a rolling split. A daily report chooses one project direction from the latest seven days of workouts plus activity, sleep, resting heart rate, and fixed class options. State only the project, intensity/recovery direction, and reason—never list exercises, sets, or reps in the daily recommendation.

Daily reports show body change only when a new measurement arrives; do not repeat the same measurement. Daily coaching must weigh all available body change, sleep, activity, completed training, and diet data together without mechanically repeating report data or adding a mental-wellbeing section. When the previous day contains a workout, act like a professional personal trainer: briefly evaluate its completion, load or stimulus from the available duration, heart-rate, volume, and project data; cross-check recovery and nutrition; then give a concrete next-step direction. Use up to three concise sentences, but never invent missing metrics or list exercises, sets, or reps. Without a previous-day workout, keep only one or two short sentences for the highest-priority action. Weekly reports must aggregate the week's actual exercise types and totals, separate recovery, training, and nutrition trends, and give a concrete next-week project schedule. Every weekly report must also give an explicit template-library decision: if unchanged, say so and explain why; if a change is recommended, show the exact before/after action or set/rep difference, the evidence, and that confirmation is pending. Never substitute a policy-only template line for an actual recommendation. It is not medical diagnosis. Persistent pain, swelling, numbness, weakness, chest symptoms, fainting, or disordered-eating signs require professional evaluation rather than training escalation.

Attribute overnight sleep only to the calendar day immediately before it ends: for a target day's recovery, use the main non-nap session ending the following morning. If that session is absent, report sleep as missing; never fall back to a same-day ending session or reuse an older night. Exclude naps and duplicate sessions. When stage data contains awake periods, calculate actual sleep from non-awake stages only when the stage totals agree with Xiaomi's duration/asleep/awake summary; if they materially conflict, use the internally consistent summary fields because some Xiaomi records mislabel deep sleep as awake. Treat activity and heart-rate data as incomplete when the last heart-rate sample stops before 18:00, and do not use those partial values in daily metrics or coaching. Apply these shared rules consistently to daily reports, weekly reports, progress bars, and training recommendations.

When a daily card is missing or has incomplete prior-day Xiaomi core data—sleep, activity, or heart rate—add a “同步后重发日报” callback button. Use the bridge's existing `cmd` event log plus the installed `BodyCoach-CardActions` watcher; the watcher must accept only the configured chat, the current report date, and one idempotent `bodycoach.resend.YYYYMMDD` action before running `daily --force`. A plain-text “重发日报” is also confirmation to resend without asking again. Do not use or invent `bridge_token` for this local watcher path.

Daily and weekly model analysis keeps the configured or default reasoning effort, waits up to 180 seconds per attempt, and retries once after a timeout, process failure, or empty output. Use the deterministic fallback only after both attempts fail.

For current weight, body composition, calorie targets, protein targets, and training advice, use the newest Xiaomi body measurement. Treat measurements in examination reports and other dated documents as historical snapshots unless they are newer than Xiaomi data. Compare timestamps before calculating and state the measurement date when the value materially affects advice.

## Personal body knowledge workflow

The private knowledge base is `.private/knowledge/BODY_KNOWLEDGE.md`. Original PDFs, images, and other files are deduplicated by SHA-256 under `.private/knowledge/sources/`; backup filenames must stay human-readable. Preserve a readable original filename, but when a bridge attachment arrives with a hash-only name, derive the filename from the knowledge-entry title and keep only a short hash suffix for collision safety. Searchable metadata and normalized metrics stay in the existing `.private/private.db`. `.private/` is gitignored. Never copy personal source material into tracked files.

Do not use a fixed category list. For every new item:

1. Decide whether it is a durable fact that may change future health, recovery, nutrition, equipment, or training advice. Ordinary meals, workouts, Xiaomi data, and Xunji data remain in their existing systems and are not duplicated here.
2. Run `knowledge status`, then `knowledge search --query <specific topic>` for comparable history. Reuse an existing primary category when its decision purpose matches; otherwise create one concise new category. Add multiple tags as needed, but only one primary category.
3. Extract and clearly separate source facts, comparison with similar history, analysis, and uncertain or unverified items. Never present an inference as a source fact. Normalize comparable numeric metrics and include their unit, reference range, abnormal flag, and source page when available.
4. For a multi-page PDF, use the PDF skill to inspect every page. Work in batches of roughly 5–10 pages when needed, retain the original file, record total page count and processed pages, and do not store full OCR text in the Markdown. The original PDF remains the source of truth.
5. Write one JSON payload and run `knowledge add --json-file ... --source-id ... --source <original-file>`. Use the bridge message ID as `source-id` when available. The command deduplicates originals, adds exact-name/unit metric comparisons, regenerates the readable document, and attempts a Lark mirror sync.
6. Give the user a concise comparison and analysis after recording. For medical material, explain uncertainty and recommend professional review when appropriate; do not diagnose.

Knowledge JSON fields are: required `record_date`, `title`, and `category`; optional `tags`, `facts`, `comparison`, `analysis`, `uncertainty`, `metrics`, `current`, `page_count`, `pages_processed`, and `source_files`. `current` is a key/value map for facts that should appear in the current snapshot; a newer entry with the same key replaces it, and an empty value removes it. A metric is `{name,value,unit,reference_range,abnormal,page}`.

Daily reports, weekly reports, meal reminders, and their model prompts must never read the knowledge tables or `BODY_KNOWLEDGE.md`. Only retrieve targeted knowledge when the user's task actually needs it. `knowledge show` is for an explicit full review; normally prefer a narrow `knowledge search` to reduce token use.

The local Markdown is the primary readable record. Its Lark document is a one-way mirror: a local write succeeds even if Lark is unavailable, failed sync is marked pending, and the next knowledge operation retries once a document is configured. Raw source files are not uploaded. Create or configure the mirror with `knowledge sync --create` or `knowledge sync --doc <url-or-token>`. Never start Lark OAuth from a group chat; ask the user to authorize in a private chat if user identity is unavailable.

The living strength-training manual is a separate editable Lark document. Configure its URL with `knowledge sync --manual-doc <url>`, which places a persistent link before the knowledge snapshot. When the user confirms a training-template change, update the applicable current-plan section in that manual and append a dated item under `更新记录` containing the before/after change and reason; then add the same confirmed change as a `训练方案` knowledge entry and sync the mirror. Keep imported source files as immutable evidence rather than rewriting them. If the manual update fails, report that the change was not fully applied.

When a scheduled weekly report was missed while the computer was unavailable, the next weekly run sends every unsent completed week oldest-first and saves progress after each successful card. A first run sends only the latest completed week.

The daily report task runs once daily at 09:30 with `StartWhenAvailable` and an explicit trigger `EndBoundary` of `2099-12-31T23:59:59`, satisfying the documented catch-up prerequisites without periodic polling. The existing `last_daily` guard skips dates already sent. Do not use a logon trigger. Automatic daily runs before 09:30 must exit without sending—even when Windows is catching up a previously missed trigger—while `daily --force` remains available for an explicitly requested resend at any time. A computer started before 09:30 therefore waits until 09:30; a missed run is queued after availability and may be delayed by Task Scheduler rather than sent immediately on login.

Run `.private/.venv/Scripts/python.exe scripts/coach.py --help` for commands. Run `doctor` for history location, missing credentials, CLI availability, Xiaomi login, or model fallback causes. Install or migrate with `powershell -File scripts/install.ps1`; preview consequential changes with `-WhatIf` first.
